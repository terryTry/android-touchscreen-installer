## 2. 背景

Android 应用开发完成后，需要交给不具备开发经验的现场人员安装到指定安卓触摸屏。当前流程通常包含：

1. 判断 Windows 是否安装了可用的 Android USB 驱动。
2. 准备 ADB Platform-Tools。
3. 打开终端并确认设备状态。
4. 远程协助现场人员执行 APK 安装、应用启动、设备重启和 Launcher 设置等命令。
5. 根据原始 ADB 错误继续排查。

该流程依赖开发人员持续远程介入，且现场人员容易在驱动、授权、设备选择、命令拼写和目标包名等环节出错。

本产品将上述流程收敛为一个自带 ADB、面向非技术人员的 Windows 图形化客户端。

## 3. 产品目标

### 3.1 核心目标

- 现场人员无需安装 Android Studio 或单独配置 ADB。
- 通过 USB 或 TCP/IP 连接指定安卓触摸屏。
- 自动识别设备状态，并将 ADB 原始错误转换为中文操作提示。
- 自动解析 APK 信息，避免手动填写包名和 Activity。
- 完成 APK 安装、更新、可选降级和安装结果验收。
- 将目标应用设置为默认 Launcher，实现开机自动进入应用。
- 提供返回、Home、最近任务、应用控制、设备重启和必要系统入口。
- 保存原系统 Launcher，支持一键恢复。
- 为远程支持保留可复制的执行结果和技术日志。

### 3.2 成功标准

在驱动和 USB 调试已满足的前提下，首次使用人员应能独立完成：

```text
连接设备
→ 选择 APK
→ 查看自动识别结果
→ 安装应用
→ 设置为开机应用
→ 重启并验证
```

整个主流程不要求现场人员输入 ADB 命令、包名或 Activity。

## 4. 用户与场景

### 4.1 主要用户

| 用户 | 特征 | 主要诉求 |
| --- | --- | --- |
| 现场安装人员 | 不熟悉 Android 开发和命令行 | 按照界面提示完成连接、安装和验证 |
| 开发/支持人员 | 熟悉 APK、ADB 和目标设备 | 远程定位问题、查看原始日志和执行高级操作 |

### 4.2 核心场景

1. 现场人员通过 USB 连接触摸屏并安装新应用。
2. 现场人员通过局域网连接固定 IP 的触摸屏并更新应用。
3. 已安装版本高于待安装 APK，需要尝试调试版降级。
4. 安装后将目标应用设为默认 Launcher。
5. Launcher 设置异常，需要恢复原系统桌面。
6. 应用异常，需要停止、重启、卸载或清除数据。
7. 设备异常，需要重启触摸屏或进入系统设置排查。

## 7. 功能需求

### 7.1 ADB 与 USB 驱动

#### ADB-001 内置 ADB

- 客户端必须携带 Windows x64 版：
  - `adb.exe`
  - `AdbWinApi.dll`
  - `AdbWinUsbApi.dll`
- 不依赖 Android Studio。
- 不要求用户配置环境变量。
- 不修改 Windows 系统 PATH。
- 所有命令必须通过绝对路径调用客户端内部 ADB。
- 界面应显示内置 ADB 是否可用及其版本。

#### ADB-002 独立运行

- 应避免与用户电脑已有 ADB Server 产生不可控冲突。
- ADB Server 启停、端口和生命周期由主进程统一管理。
- `5038` 已存在健康 ADB Server 时应直接复用，不得因残留 Server 阻断应用启动。
- `5038` 被非 ADB 服务占用时，应自动从 `5039–5048` 选择可用端口并向用户展示
  实际端口。
- 客户端退出时不得误杀不属于本客户端的其他 ADB Server。
- 正常退出、终端中断、`SIGTERM` 和非 Windows 平台的 `SIGHUP` 应触发本客户端
  所启动 ADB Server 的尽力清理；无法清理的异常退出由下次启动复用机制恢复。

#### DRV-001 OEM USB 驱动

USB 驱动与 ADB Platform-Tools 为不同交付物。

- 只有获得目标触摸屏厂商提供的已签名驱动包后，才允许集成一键安装。
- 驱动包必须与目标 VID/PID 和 Windows x64 匹配。
- Electron 主程序不得长期以管理员权限运行。
- 仅在安装驱动时通过 `pnputil` 申请 UAC。
- 不修改通用 INF 来模拟“万能驱动”。
- 客户端必须区分三类信息：ADB 客户端版本、`adb devices -l` 返回的实际 USB ADB
  识别状态、安装包是否内置 OEM 驱动包。
- 未提供合格驱动包时，只显示“未内置 OEM 驱动包”及排查指导，不得在已经通过 USB
  正常连接设备时显示“驱动待配置”或将其判定为连接故障。
- 实际 USB ADB 状态应覆盖可用、等待授权、离线、访问受限、未检测到设备等结果。

该功能的最终验收依赖第 15 节中的硬件资料。

### 7.2 设备连接

#### DEV-001 USB 连接

- 启动后自动检测 USB ADB 设备。
- 不提供手动刷新按钮。
- USB 插拔后应自动更新设备状态。

#### DEV-002 TCP/IP 连接

- 支持输入设备 IP 和端口。
- 默认端口为 `5555`。
- 端口允许修改，范围为 `1–65535`。
- 支持连接和断线后的重新连接。
- 保存最近成功连接的 IP 和端口。
- 不实现 Android 11 动态配对码流程。

#### DEV-003 设备状态

至少识别以下状态：

| 状态 | 界面提示 |
| --- | --- |
| 未检测到设备 | 请检查 USB、USB 调试或驱动 |
| `unauthorized` | 请在触摸屏上勾选“始终允许”并点击允许 |
| `offline` | 设备连接异常，请重新插拔 USB 或重新连接 |
| `device` | 设备已连接，可以执行操作 |
| 多设备 | 必须选择目标设备后才能继续 |
| TCP 失败 | 显示目标 IP、端口和连接错误 |

#### DEV-004 目标设备锁定

- 多设备时必须明确选择目标设备。
- 所有设备相关命令必须由命令执行器自动携带目标序列号。
- React 渲染进程不得自行拼接序列号或命令参数。
- 正在安装或执行高风险操作时，不允许无提示切换目标设备。

#### DEV-005 设备信息

连接成功后至少显示：

- 厂商。
- 型号。
- 设备名。
- 序列号。
- Android 版本。
- API Level。
- ABI 列表。
- 当前连接方式。

### 7.3 设备导航

#### NAV-001 返回

- 提供“返回”按钮。
- 对应 Android `KEYCODE_BACK`。
- 操作不需要二次确认。

#### NAV-002 Home

- 提供“Home”按钮。
- 对应 Android `KEYCODE_HOME`。
- 操作不需要二次确认。

#### NAV-003 最近任务

- 提供“最近任务”按钮。
- 对应 Android `KEYCODE_APP_SWITCH`。
- 厂商系统不支持时显示明确提示。

### 7.4 目标应用与 APK 选择

#### TGT-001 读取设备已安装应用

- 目标应用与待安装 APK 必须解耦；应用控制和 Launcher 管理不强制要求本地 APK。
- 必须支持以下四类指定方式：
  - 从设备应用列表选择：只列出用户 0 中具有 `MAIN/LAUNCHER` 或 `MAIN/HOME` Activity 的应用，支持按包名或 Activity 搜索。
  - 使用当前前台应用：解析当前恢复的 Activity；无法可靠识别时保留原目标并提示用户先打开应用。
  - 使用当前桌面：读取当前 Launcher 包名并设为目标。
  - 选择或拖入 APK：自动解析包名；如果设备中已安装同包名应用，无论版本是否与 APK 相同，都可直接操作设备现有版本。
- 保留完整包名输入，作为指定没有桌面入口应用的补充方式。
- 从设备指定应用后，必须通过 `dumpsys package <包名>` 读取并去重
  `requested permissions`，同时回读 Package Manager 与 AppOps 实际授权状态；
  不得因为没有本地 APK 而隐藏权限区域。
- 应用信息区展示版本、包名、启动组件和 HOME 信息，不展示权限列表或权限数量。
- `dumpsys` 不提供原 Manifest 的 `maxSdkVersion` 时应明确说明该限制，不得伪造
  上限值。
- 选中目标后查询 Android 用户 0 中对应包名的安装状态、版本、启动 Activity 和 HOME Activity。
- 读取成功后按“设备序列号 + Android 用户”记忆目标包名；再次连接同一设备时自动恢复。
- 应用列表刷新、当前前台识别或包名读取失败时，不得清除当前已选择的 APK 或目标应用。
- 未解析到启动 Activity 时禁用启动和重启，但停止、卸载和清除数据仍可用。
- 未解析到 HOME Activity 时禁用设置和验证开机应用。
- 选择 APK 后将 APK 对应包名切换为当前目标应用，并记忆到当前设备。
- 不提供手工输入 Activity 组件的入口。

#### APK-001 APK 选择

- 支持文件选择器选择 `.apk` 文件。
- 支持将 `.apk` 文件拖入安装区域。
- 非 APK 文件必须拒绝并显示原因。

#### APK-002 自动解析

选择 APK 后自动解析最终 Manifest，至少显示：

- 应用名称。
- 应用图标。
- `applicationId`。
- `versionName`。
- `versionCode`。
- `minSdk`。
- `targetSdk`。
- APK 支持的 ABI。
- HOME Activity。
- HOME Activity 的 `exported` 状态。
- `<uses-permission>` 权限名及 `maxSdkVersion`。

普通模式不得要求现场人员填写包名或 Activity。

#### APK-003 HOME Activity 识别

HOME Activity 必须同时包含：

- `android.intent.action.MAIN`
- `android.intent.category.HOME`
- `android.intent.category.DEFAULT`

处理规则：

| 结果 | 行为 |
| --- | --- |
| 未找到 | 禁用“设为开机应用”，提示 APK 未实现桌面能力 |
| 找到一个 | 自动使用 |
| 找到多个 | 要求开发/支持人员选择 |
| `exported` 不为 `true` | 提示 Manifest 配置错误 |

#### APK-004 兼容性预检

安装前至少检查：

- APK `minSdk` 不高于设备 API Level。
- APK 包含的原生 ABI 与设备 ABI 兼容。
- 设备是否已安装同包名应用。
- 待安装 `versionCode` 与已安装版本的关系。

预检失败时不得直接执行安装。

#### APK-005 系统部署权限校验

- 不再提供“应用权限与当前设备”面板或“准备应用权限”工作流。
- 保留 APK Manifest、设备 Package Manager 权限定义及授权状态的内部解析，供
  特权应用部署生成最小白名单和部署后回读验收。
- 权限定义不可靠时阻止特权部署；权限检测本身不得修改设备。
- 运行时权限和特殊访问由用户在设备端授权。

#### APK-006 Root 通道与系统应用部署

- 读取并显示 `ro.build.type`、`ro.debuggable`、Verified Boot 状态、Bootloader
  锁状态、当前 adbd UID、`su` 路径和已验证的 Root 通道。
- `userdebug/eng` 且 `ro.debuggable=1` 时优先尝试标准 `adb root`；命令返回
  “restarting adbd as root”后仍必须通过 `shell id` 验证 `uid=0`，不能只依据
  命令提示。
- 如果 adbd 回读仍为 shell，或当前构建不支持标准 `adb root`，但设备中存在
  `su`，则使用设备实际返回的路径执行 `su 0 id`。只有回读 `uid=0` 后才将 Root
  通道标记为可用；不得假设 `su -c` 与目标固件兼容。
- 手动系统应用部署作为高级备用路径，必须同时满足：
  - 已选择并解析 APK。
  - `adbd uid=0` 或 `su 0` Root 通道已通过回读验证。
  - 当前设备在线且没有同包名的工具托管部署记录。
- 提供两个互斥部署模式：
  - “系统应用（推荐）”写入
    `/system/app/AdbTool_<安全包名>/base.apk`，重启后验收 `SYSTEM` 或
    `UPDATED_SYSTEM_APP` 身份。此模式不生成白名单，也不得声称可以获得
    `PRIVILEGED` 或平台签名权限。
  - “特权应用”写入
    `/system/priv-app/AdbTool_<安全包名>/base.apk`。该模式还要求当前设备权限
    定义已成功读取，以生成可靠的最小白名单，并在重启后验收
    `SYSTEM/PRIVILEGED`。
- adbd Root 通道通过 `adb remount` 处理系统分区；`su` Root 通道先执行
  `su 0 /system/bin/remount`。如果输出明确要求重启以启用 overlayfs，工具应完成
  首次重启、重新验证 Root，再执行 `su 0 /system/bin/remount system`，并通过
  Root 通道验证 `/system` 实际可写后才继续。如果厂商 Remount 返回失败或完成后
  `/system` 仍不可写，可在已经回读为 `uid=0` 的同一通道内尝试
  `mount -o remount,rw /system`；仍须再次回读最终可写状态，不能只依据退出码。
- 检测到只读分区、需要关闭 verity、权限不足或 overlayfs 空间不足时立即停止；
  不得自动关闭 Verified Boot。
- 目标目录已存在但无托管记录时禁止覆盖。
- 只为 APK 实际请求且设备标记为 `privileged` 的权限生成最小化
  `privapp-permissions-adbtool-*.xml`；纯 `signature` 权限不得加入白名单并声称
  可获得。
- 应用目录必须设置 `root:root`、`0755`；APK 和白名单必须设置 `root:root`、
  `0644`，并执行 `restorecon`。
- 第一次写入系统分区前保存“设备序列号 + 包名 + 部署模式 + 确定路径 + 版本”的托管记录；
  后续步骤中途失败时也必须保留该记录，使用户可以安全回滚。
- 系统写入前必须同时读取活动 `package:` 路径、全部 `codePath`、`SYSTEM`、
  `UPDATED_SYSTEM_APP` 和 `PRIVILEGED` 状态。设备活动 `versionCode` 高于所选 APK
  时必须在 Remount 前阻止操作，因为较低版本系统副本不能覆盖 `/data/app` 活动更新；
  检测到同包名非托管 `/system/app` 或 `/system/priv-app` 副本时也必须阻止创建第二个
  系统目录，并给出先彻底卸载旧系统副本或由固件工程师迁移的处理路径。
- 写入后重启设备，通过 `dumpsys package` 验证实际 `versionCode` 和对应模式
  所需标志；特权模式还必须回读 APK 实际请求的 privileged 权限授予状态。
- 系统应用部署不得清除现有应用数据。设备已存在同签名 `/data/app` 版本时允许
  Android 将其识别为 `UPDATED_SYSTEM_APP`；回滚系统副本后保留普通安装版本。
- Root、Remount、部署和回滚均属于高风险操作，必须显示系统无法启动和需要刷机
  恢复的风险；部署和回滚还必须二次勾选确认。
- 系统/特权应用通过高级操作区显式部署，独立确认系统分区修改与重启风险。

- 回滚只能删除经过托管记录和确定路径双重校验的文件；禁止接受用户输入任意系统
  路径。删除后重启并验证托管目录不存在即可清除托管记录；如果固件原本还有其他
  同包名系统副本，应明确报告 `SYSTEM` 身份仍保留，不得把来源不明的固件副本误判为
  回滚失败，也不得在回滚工作流中删除它。
- 本功能不处理解锁 Bootloader、刷写 boot/system 镜像、Magisk 安装或平台重签名。

### 7.5 APK 安装

#### INS-001 安装或更新

- 主操作为“安装/更新”。
- 默认使用覆盖安装并保留数据的模式。
- 安装前显示目标设备、APK 名称、包名和版本。
- 用户确认后开始安装。
- 显示传输、安装和验证阶段。
- 提供执行耗时。

#### INS-002 可选降级

- 高级操作中提供“允许调试版 APK 降级安装”选项。
- 默认关闭。
- 仅在待安装 `versionCode` 低于已安装版本时显示或启用。
- 执行前明确提示降级可能被设备拒绝。
- `-d` 只保证用于 debuggable 应用，不承诺 release APK 能降级。
- 降级失败时提供：
  - 取消。
  - 卸载后重装。
- 选择卸载后重装时，必须提示应用数据会被清除。

#### INS-003 安装验证

ADB 返回安装成功后，还必须查询设备中的实际包信息并验证：

- 包名正确。
- `versionCode` 与目标 APK 一致。
- 应用处于已安装状态。

仅在验证通过后显示“安装成功”。

#### INS-004 安装错误映射

至少将以下错误转换为中文：

| 原始错误 | 中文提示 |
| --- | --- |
| `INSTALL_FAILED_VERSION_DOWNGRADE` | 当前设备版本更高，普通覆盖安装不允许降级 |
| `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | 新旧应用签名不一致，卸载重装会清除数据 |
| `INSTALL_FAILED_INSUFFICIENT_STORAGE` | 设备存储空间不足 |
| `INSTALL_FAILED_OLDER_SDK` | 设备 Android 版本低于 APK 要求 |
| `INSTALL_FAILED_NO_MATCHING_ABIS` | APK 与设备 CPU 架构不兼容 |
| `INSTALL_PARSE_FAILED_*` | APK 文件无效或 Manifest 无法解析 |
| `device offline` | 设备连接已中断 |
| `unauthorized` | 设备尚未授权当前电脑 |
| `no devices/emulators found` | 未检测到可用设备 |

#### INS-005 签名冲突恢复

- 检测到 `INSTALL_FAILED_UPDATE_INCOMPATIBLE` 时，不允许重复执行无效的覆盖安装。
- 显示“卸载旧版并重装”恢复入口，并明确提示旧应用及其本地数据会永久删除。
- 用户必须勾选数据丢失确认项后才能执行恢复。
- 先将 APK 传输到设备，再卸载旧应用；卸载成功后执行全新安装和版本回读。
- 如果目标应用是当前默认 Launcher，必须先在设备系统设置中切换到其他默认桌面，不允许直接卸载。
- 卸载后仍检测到同包名应用时停止流程，提示系统应用或多用户安装的可能性。
- 卸载完成但新 APK 安装失败时，必须明确说明旧应用和数据已经删除，并将安装状态回读为未安装。
- 签名冲突未解决前，禁用覆盖安装、启动、重启、设置 Launcher 和 Launcher 验证；停止、卸载和清除旧应用数据仍可用。

### 7.6 应用运行管理

#### APP-001 启动应用

- 通过自动识别的组件启动目标应用。
- 不要求用户输入 Activity。
- 启动失败时显示包名、组件和错误原因。

#### APP-002 停止应用

- 提供“停止应用”按钮。
- 执行前二次确认。

#### APP-003 重启应用

- 提供“重启应用”按钮。
- 流程为停止应用后重新启动。
- 任一步失败时停止工作流并显示失败步骤。

#### APP-004 卸载应用

- 放置在高级操作区。
- 执行前显示包名并进行危险操作确认；确认文案必须说明系统应用会修改 `/system`、
  自动重启，并且只能通过重新安装或刷写固件恢复，用户必须额外勾选接受该风险。
- 默认按清除应用数据的标准卸载流程处理。
- 普通应用执行标准卸载后必须重新查询包状态，不能只依据 `Success` 宣称完成。
- 对 updated system app，标准卸载成功仅表示 `/data/app` 更新已移除；如果应用回退到
  固件系统副本，必须继续进入系统应用卸载流程。
- 系统应用卸载仅支持 Package Manager 明确回读到
  `/system/app/<目录>` 或 `/system/priv-app/<目录>` 的路径。流程为停止应用、清除
  用户 0 数据、`pm uninstall --user 0`、验证 Root/Remount、删除前再次核对包名与
  `codePath`、精确删除已确认目录、`sync`、重启，并使用
  `pm list packages -u <包名>` 和目录状态共同验收。
- 如检测到 `/product`、`/vendor`、`/system_ext` 或其他未受支持分区中的副本，必须
  停止并交由固件工程师处理，不得扩展为任意路径删除器。

#### APP-005 清除应用数据

- 放置在高级操作区。
- 明确提示操作不可恢复。
- 执行前进行危险操作确认。
- 清除完成后重新查询包状态。

### 7.7 Launcher 管理

#### LCH-001 查询当前 Launcher

- 自动查询 Android 用户 `0` 的当前 HOME。
- 显示当前 Launcher 包名。
- 设置前记录原 Launcher。

#### LCH-002 设置开机应用

- 仅当 APK 和设备均确认存在可用 HOME Activity 时启用。
- 执行前提示：
  - 开机后会进入目标应用。
  - 按 Home 键也会进入目标应用。
- 用户确认后，将目标包设置为 Android 用户 `0` 的默认 HOME。
- 不禁用或卸载原系统 Launcher。

#### LCH-003 立即验证

- 设置成功后模拟 Home 键。
- 再次查询当前 HOME。
- 查询结果必须与目标包一致。

#### LCH-004 重启并验证

- 用户确认后重启设备。
- 等待设备断开并重新连接。
- 设备恢复后自动查询当前 HOME。
- 验证成功或失败均必须提供明确结果。

#### LCH-005 切换其他默认桌面

- 不提供“恢复系统桌面”按钮或恢复点展示。
- 用户需要切换桌面时，通过“系统设置”在设备端选择其他默认桌面。
- 目标应用是当前默认桌面时，继续阻止直接卸载或卸载重装，并提示先切换桌面。

### 7.8 设备与系统

#### SYS-001 重启设备

- 提供“重启设备”按钮。
- 执行前二次确认。
- 执行后进入等待设备重新连接状态。
- 不提供重启到 Recovery 或 Bootloader。

#### SYS-002 打开系统设置

- 提供“系统设置”按钮。
- 打开 Android 系统设置首页。
- 厂商系统没有可用页面时显示不支持。

#### SYS-003 打开开发者选项

- 提供“开发者选项”按钮。
- 厂商系统没有可用页面时显示不支持。

### 7.9 日志和结果

#### LOG-001 当前结果

- 标题栏必须提供滚动页面时仍可访问的“最近操作 / 操作记录”入口。
- 入口展示当前执行中操作；无执行中操作时展示最近一次已完成操作摘要。
- 摘要使用面向现场人员的中文描述。
- 成功、处理中、失败必须具有清晰状态差异。

#### LOG-002 操作历史与技术日志

- 必须按“用户发起的一次操作”记录历史，而不是只展示若干条分散的 ADB 命令。
- 最近 100 次操作必须跨应用重启保留，按时间倒序查看，并支持只看失败操作。
- 历史列表只传输轻量摘要；选择记录后再按需读取该次操作的诊断步骤，避免历史输出
  随每次设备刷新重复传输。
- 每条记录必须展示操作名称、成功/失败、结果摘要、下一步建议、目标设备、连接
  方式、目标应用、时间和耗时。
- 每次操作最多保留 25 条诊断步骤；单条标准输出和标准错误分别限制为 1,000 个
  字符。完整文件日志仍遵循应用日志轮转策略。

技术日志至少包含：

- 时间。
- 客户端版本。
- ADB 版本。
- 目标设备序列号。
- 连接方式。
- 操作名称。
- 实际执行参数，敏感信息除外。
- 标准输出。
- 标准错误。
- 退出码。
- 耗时。

#### LOG-003 复制执行结果

- 不提供语义不明确的单一“复制结果”按钮。
- 每条历史记录分别提供：
  - “复制操作摘要”：包含操作、中文结果、下一步建议、设备、目标应用和时间，适合
    向同事说明执行情况，不包含 ADB 原始输出。
  - “复制诊断详情”：在操作摘要基础上增加 ADB 参数、退出码、耗时、标准输出和
    标准错误，并明确标注仅用于提交给开发或技术支持人员排查。
- 界面必须在按钮旁说明两种复制内容的用途和诊断详情包含的信息。
- 不复制与当前问题无关的设备隐私数据。

### 7.10 命令注册机制

#### CMD-001 内置命令

V0.1 的所有操作通过内置命令注册表管理，不在 React 组件中直接拼接命令。

命令注册信息至少包含：

- 唯一 ID。
- 显示名称。
- 命令类型。
- 参数模板。
- 风险等级。
- 超时时间。
- 是否需要目标设备。
- 是否需要 APK 或包名。
- 结果解析器。

#### CMD-002 命令类型

内部至少支持：

- ADB 主命令。
- Android Shell 命令。
- 多步骤工作流。

#### CMD-003 安全约束

- 按钮提交命令 ID 和经过校验的输入；终端提交命令文本和会话 ID，由主进程校验
  子命令、设备与 Server 归属，通过专用 IPC 传输会话输入和输出。
- 命令只在 Electron 主进程执行。
- 不使用 `shell: true`。
- 不允许执行任意本地程序。
- 不允许 CMD、PowerShell 或批处理脚本。
- 所有占位参数必须按类型校验。
- 同一设备上的安装和危险操作必须串行执行。
- 手动终端使用独立会话执行层，固定实际 ADB 路径和 Server 端口；会话期间暂停
  其他设备操作，退出后刷新设备状态。终端输入不沿用按钮工作流的业务确认与验收。

## 8. 关键流程

### 8.1 USB 安装流程

```text
启动客户端
→ 检查内置 ADB
→ 自动检测 USB 设备
→ 如未授权，指导用户在触摸屏确认

```

```text
选择 TCP/IP
→ 输入 IP

→ 连接设备
→ 选择 APK
→ 解析、预检、安装与验收
```

```text

→ 设置目标包为 HOME

→ 查询当前 HOME
→ 可选重启设备
→ 设备重连后再次验证
```

通过工具打开系统设置 → 在设备端选择其他默认桌面 → 按 Home 键确认进入该桌面。

## 10. 数据与本地存储

客户端允许保存：

- 最近成功使用的 TCP 地址和端口。
- 按设备序列号记录的原 Launcher。
- 客户端配置。
- 滚动技术日志。

不得保存：

- ADB 私钥以外的用户凭据。
- 触摸屏中的业务数据。
- 未经需要采集的文件、图片或完整设备信息。

日志必须设置大小或时间滚动策略，具体阈值在技术设计阶段确定。

## 11. 非功能需求

### 11.1 安全

- Electron 必须启用 `contextIsolation`。
- Renderer 禁用 Node.js 集成。
- 使用受限 preload API。
- IPC Handler 必须校验调用来源和输入。
- 外部链接不得在应用内任意导航。
- ADB、文件系统和进程能力只存在于主进程。
- Windows 管理员权限只用于明确的驱动安装动作。

### 11.2 可靠性

- 每个命令必须具有超时和可识别的结束状态。
- ADB 断开时不得继续执行后续工作流。
- 同一设备的安装、卸载、清除数据和 Launcher 变更必须串行执行。
- 客户端异常退出不得留下无法识别的安装状态。
- 设置 Launcher 前必须成功保存原 Launcher。

### 11.3 易用性

- 普通流程不展示原始 ADB 命令。
- 每个失败状态必须提供下一步建议。
- 危险操作不得使用模糊按钮文案。
- 高级操作必须使用独立的
  警示色背景和边框，并显示风险说明。
- 界面应适配常见 Windows 缩放比例。
- 主操作区域在 1366×768 分辨率下可完整使用。

### 11.4 性能目标

- 客户端启动后应尽快显示可交互界面，ADB 初始化不得阻塞首屏。
- 已连接设备状态变化应在数秒内反馈。
- 安装过程中 UI 不得无响应。
- 大 APK 的传输进度应持续更新。

- 可通过 USB 或 TCP/IP 连接真实触摸屏测试主要业务流程。

### 12.2 Windows 验收环境

最终必须在真实 Windows 10/11 x64 环境验证：

- 内置 Windows ADB。
- USB 驱动。
- USB 插拔和授权。
- UAC。
- Windows Defender 和 SmartScreen。
- Launcher 设置与验证。

### 12.3 发布物

V0.1 主要发布物：

- 未签名的 Windows x64 NSIS 安装包。
- 对应 SHA-256 校验值。
- 版本说明。

未签名安装包可能显示“未知发布者”或 SmartScreen 警告，该风险作为已知交付条件接受。
